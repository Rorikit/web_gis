# Обзор проекта

## Назначение

`web_gis` — система учёта повреждений теплосетей и ордеров на их устранение для городского
теплоснабжающего предприятия (Рязань). Проект поддерживает регистрацию повреждений, ведение
ордеров, привязку объектов к GIS-точкам на карте, разграничение доступа по районам и ролям,
а также формирование регламентных отчётов (DOCX-карта повреждения, XLSX-справка).

## Стек

- **Backend**: Django 6 + Django REST Framework, PostgreSQL/PostGIS, Gunicorn.
- **Frontend**: React 19 + TypeScript, Vite, TanStack Query, TanStack Table, React Hook Form + Zod,
  Zustand, OpenLayers для карт.
- **Инфраструктура**: Docker Compose (dev и production-профили), Nginx как reverse proxy и раздача
  статики SPA, PostGIS как основная СУБД.

Подробности production-развёртывания — в `DEPLOY.md` в корне репозитория.

## Доменная модель

Центральная сущность backend — модель `Damage` (`apps.incidents.models.Damage`). Одна и та же
запись одновременно представляет и «повреждение», и связанный с ним «ордер»: у неё есть поля
и для описания повреждения (`heat_source`, `damage_description`, `network_type`, ...), и для
ордера (`order_number`, `order_opened_at`, `order_kind`, `area_state`, ...). Разделение на два
раздела UI («Повреждения» и «Ордера») выполняется только на уровне сериализации и списковых
endpoint'ов (`serialize_damage` / `serialize_order`, `DamageListCreateView` / `OrdersListView`) —
это одна и та же таблица в БД.

К повреждению/ордеру может быть привязана GIS-точка (`GisPoint`, OneToOne к `Damage`) и фотографии
(`Photo`). Каждое изменение значимых полей фиксируется в `AuditEvent` для истории изменений.

## Районы и права доступа

Справочник `District` (`apps.accounts.models.District`) задаёт административные районы города.
Каждый пользователь (`UserProfile`) имеет роль и опционально привязан к одному району. Ролей пять:

- `district_damage` — работа с повреждениями своего района;
- `district_order` — работа с ордерами своего района;
- `oopppr` — доступ на чтение по всем районам, формирование справок;
- `full_access` — полный доступ по всем районам;
- `admin` — то же самое плюс управление пользователями.

Матрица прав по действиям определена в `apps.accounts.permissions.PERMISSION_MATRIX` на backend
и продублирована на frontend в `src/features/permissions/model/permissions.ts` — при изменении
правил обе стороны нужно обновлять синхронно.

## GIS-точки и определение адреса

Указание точки на карте выполняется через `OpenLayers` в модальном окне выбора точки
(`GisPointPicker` на frontend). При клике по карте адрес автоматически определяется через
обратное геокодирование OpenStreetMap Nominatim и подставляется в поле «Адрес» соответствующей
карточки. Сохранение координат идёт через отдельные endpoint'ы:

- `POST /gis/damages/{id}/point` — для повреждений (проверяет право `damage.update`);
- `POST /gis/orders/{id}/point` — для ордеров (проверяет право `order.update`).

Оба используют общую функцию `apps.incidents.views.save_gis_point`. Адрес GIS-точки при отдаче
клиенту всегда берётся из актуального поля `address` родительской записи, а не из когда-то
сохранённого снимка — это исключает расхождение между «Адрес» и «Адрес GIS» в карточке.

## Отчёты

Модуль `apps.incidents.reports` формирует два типа файлов без внешних шаблонов:

- DOCX «Карта повреждения» (`python-docx`) — таблица всех полей конкретного повреждения плюс
  свободный текст дополнительных сведений;
- XLSX «Справка» (`openpyxl`) — два листа (повреждения и ордера) со сводкой по текущим
  (неархивным) записям на дату отчёта.

## Frontend-архитектура

Frontend организован по Feature-Sliced-подобной структуре в `src/`:

- `app/` — роутинг, guard-компоненты (`AuthGuard`, `RoleGuard`), layout'ы;
- `pages/` — страницы-контейнеры, привязанные к маршрутам;
- `widgets/` — крупные составные блоки (карточка повреждения/ордера, карта);
- `features/` — бизнес-логика и переиспользуемые UI-блоки в разрезе доменов (auth, damages,
  orders, gis, permissions, reports, users, audit-history);
- `entities/` — типы доменных сущностей;
- `shared/` — API-клиент, общие UI-компоненты, константы, утилиты.

## Что генерируется автоматически

При сборке документации Sphinx подключает Django (`django.setup()`) и берёт docstring прямо
из исходников backend через `autodoc`/`autosummary`. Frontend (TypeScript/React) в эту
документацию не автогенерируется — Sphinx ориентирован на Python-код; архитектура frontend
описана здесь вручную и обновляется при значимых структурных изменениях.
